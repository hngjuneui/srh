# Rally Lab — 배드민턴 테스트 웹앱

스마트폰에서 보낸 프레임을 PC의 MediaPipe/OpenCV로 분석하고 결과를 되돌려 받는 실제 동작 프로토타입입니다. 두 모드는 **영상 분석**과 **자동 스코어**입니다. 임의 점수나 샘플 분석 결과를 실제 분석처럼 표시하지 않습니다.

## 실행

공개 웹 화면: [Rally Lab](https://rally-lab.hngjuneui.workers.dev). **현재 PC 외부 연결은 승인 대기 중이므로 원격 분석은 아직 사용할 수 없습니다.** 배포 구성과 재배포 방법은 [DEPLOYMENT.md](DEPLOYMENT.md)를 참고하세요.

Windows / Python 3.12 권장. 현재 작업 PC에는 `.venv`와 포즈 모델 설치를 완료했습니다.

```powershell
./start.ps1
```

[PC에서 앱 열기](http://127.0.0.1:8765). 실행 터미널에 표시되는 8자리 코드로 로그인합니다. 코드는 `data/access-code.txt`에 보관됩니다. 서버를 재시작하면 로그인은 다시 해야 합니다.

다른 PC에서 처음 설치한다면:

```powershell
./setup.ps1 -PythonPath "C:/path/to/python.exe"
./start.ps1
```

`setup.ps1`는 패키지와 Google 공식 MediaPipe Pose Landmarker Lite 모델을 다운로드합니다. 테스트 당시 설치 버전은 `requirements-lock.txt`에 기록했습니다. 별도의 셔틀 검출 모델이나 자세 품질 모델을 학습한 것은 아닙니다.

## 구현한 기능과 현재 범위

| 기능 | 현재 동작 | 아직 검증/구현이 필요한 부분 |
|---|---|---|
| 영상 분석 모드 | PC 파일 업로드, 서버 포즈 분석, 오버헤드 스윙 후보, 구도 피드백 | 클리어/스매시 자동 구분, 정확한 타점·그립·3D 회전·자세 품질 평가 |
| 원격 카메라 | WSS/WS로 표본 JPEG 전송, PC 추론, 프레임에 맞춘 Canvas 표시 | 외부 HTTPS 경로 설정, 실제 LTE/5G 시험, WebRTC/TURN |
| 자동 스코어 | 세 가지 휴리스틱 개별 on/off, 근거 강도·합의 기준, 보류, 점수 자동 기록 | 경기 영상에서의 승자 판정 정확도 검증, 학습된 셔틀 추적 |
| X 수정 | 최대 4인 포즈에서 X 후보, 1.2초 유지, 종료 후 15초 이내 한 번, 직전 득점 팀 변경 | 실제 네 명의 가림·원거리·카메라 각도 검증 |
| 하이라이트 | 업로드 영상의 랠리 후보 구간, 선택/시간 편집, 이어보기, MP4 합치기 | 준비/줍기 구간의 완전한 자동 제외, 원본 오디오 유지 |
| 녹화 | 브라우저 원본 다운로드, 이후 PC 업로드 | 백그라운드/장시간 안정성, 끊김 구간 자동 복구, 녹화 중 서버 자동 저장 |
| 점수판 | 수동 득점, 취소, 직전 득점 교체, 서브 팀, 게임 수, 재시작 후 기록 복원 | 복식 개인별 서버/리시버 회전, 공식 대회별 규칙 프로필 |

기본 규칙은 21점·2점 차·30점 상한·2게임 선승의 **연습용 프리셋**입니다. 목표 점수는 첫 득점 전에 설정할 수 있습니다. 최신 공식 규칙 적용을 주장하지 않습니다. 코트가 바뀌면 설정에서 가까운 쪽 팀도 바꾸세요.

## 첫 테스트 순서

1. PC 브라우저에서 앱을 열고 연결 코드 입력.
2. **영상 불러오기**로 직접 촬영한 MP4/MOV/WebM 업로드(최대 512 MB, 2시간). 파일은 연결한 PC에 저장되고 약 8fps 표본으로 분석됩니다.
3. 분석 완료 후 랠리 후보를 확인. 없으면 구간 추가, 잘못 잡히면 시작/끝 시간을 수정. **모아서 재생**과 **MP4 내보내기**로 결과를 확인합니다. MP4 하이라이트는 현재 음성이 없습니다.
4. **카메라 연결**로 PC 왕복과 처리 시간 확인. 기본 전송은 너비 960px, 최대 8fps. 화면 표시 속도와 수신 빈도는 다를 수 있습니다. 첫 몇 프레임은 모델 준비 때문에 느립니다.
5. 자동 스코어 모드에서 **코트 지정**을 누르고 가까운 왼쪽 → 가까운 오른쪽 → 먼 오른쪽 → 먼 왼쪽 모서리를 순서대로 누릅니다. 카메라 이동 후에는 다시 지정합니다.
6. 설정에서 알고리즘을 조합합니다. 기본 합의 설정은 다른 신호 종류 2개 이상이 맞아야 기록합니다. 기준을 낮추고 단일 근거를 허용하면 더 자주 기록되지만 오판도 늘어납니다.
7. 우선 수동으로 B팀에 한 점을 추가한 뒤 랠리하지 않는 상태에서 정면을 향해 양팔 X를 1.2초 유지해 A팀으로 바뀌는지 시험합니다. 정지 화면 반복·미검출·1초 초과 수신 공백은 X 유지 시간을 끊습니다.
8. 실제 경기에서는 정확한 수동 점수 기록을 따로 두고 오판, 보류, 수정 횟수를 비교합니다.

업로드 원본은 보존하고 브라우저 재생용 H.264/AAC MP4를 별도로 생성합니다. 지원되는 MOV/HEVC도 이 과정을 거칩니다. 긴 영상은 재생본 준비 시간이 추가되며, 손상된 파일이나 지원되지 않는 디코더는 오류로 표시합니다.

## 통신사망 ↔ 유선 PC

PC가 Wi-Fi일 필요는 없습니다. 휴대폰에서 접근 가능한 **HTTPS 주소가 PC의 `127.0.0.1:8765`에 연결**되어야 합니다. 현재 외부 공개 주소는 설정하지 않았습니다. `127.0.0.1`을 휴대폰에 입력하면 휴대폰 자신을 가리키므로 이 PC에 연결되지 않습니다.

테스트용 HTTPS 역방향 터널/프록시에 필요한 조건:

- HTTPS/WSS 및 WebSocket 업그레이드 전달.
- 업로드 제한 512 MB 이상 또는 작은 영상을 사용.
- 분석 시 응답 대기 시간을 충분히 허용.
- 기존 연결 코드 인증 유지. 공개 인터넷에 개발 서버를 무인 노출하는 운영 구성은 별도로 검토.

이 버전은 JPEG 표본 전송이므로 외부 WSS 경로만 열리면 WebRTC ICE/NAT 협상 없이 분석을 시험할 수 있습니다. 한 번에 한 프레임만 전송하고 응답을 받은 후 다음 프레임을 보냅니다. 느려질 때 대기 프레임이 계속 쌓이지 않습니다. 프레임 단절 동안에는 득점/제스처 근거를 이어 붙이지 않습니다.

후속 WebRTC 구현에는 시그널링 + STUN + **TURN 중계**가 필요합니다. HTTPS 터널은 WebRTC 미디어용 TURN의 대체재가 아닙니다. 통신사 NAT 및 PC 측 공유기 때문에 직접 경로가 안 열릴 수 있습니다. [WebRTC TURN 문서](https://webrtc.org/getting-started/turn-server)

실측 대상은 왕복+분석 지연, PC 처리 시간, 수신 fps, 업로드 Mbps, 장시간 끊김입니다. 1 Mbps의 지속 업로드는 오버헤드 제외 약 **450 MB/시간**입니다. 사진 복잡도에 따라 JPEG 크기가 달라집니다. 고속 셔틀 추적의 검증용으로 저fps 전송을 사용하지 마세요.

PC 수신 확인: 휴대폰과 PC에서 **같은 경기 주소**를 열고 각각 연결 코드로 로그인합니다. PC 페이지에 마지막 수신 영상과 분석 상태가 표시됩니다. 두 기기가 동시에 같은 경기에 카메라를 켜면 두 번째 전송은 거절합니다. PC 모니터는 2초마다 갱신하므로 정밀 동기화 오버레이를 표시하지 않습니다. 송신 휴대폰의 분석 프레임은 프레임 ID로 동기화합니다.

## 클리어 분석 기준

앱의 촬영 가이드와 [RESEARCH.md](RESEARCH.md)에 코칭 출처와 제품 비교를 정리했습니다. 기본 범위는 **일반 포핸드 오버헤드 클리어 연습**입니다. 다음을 구별합니다.

- 관찰: 팔의 준비, 손목의 영상상 이동, 오버헤드 스윙 후보, 인물 크기·전신 가시성.
- 코칭 참고: 측면 준비, 몸 회전과 스윙의 연결, 어깨 위쪽 타점, 복귀.
- 측정 불가: 손목 위치를 셔틀 타점으로 바꿔 해석하기, 그립, 실제 라켓 접촉, 깊이, 정밀 3D 회전, 학습되지 않은 자세 점수.

클리어 자세용 구도는 한 선수를 크게 담는 측면/대각 측면, 스코어용 구도는 네 선수를 담는 후방 전체 코트입니다. 한 구도로 두 목적의 정확도를 동시에 보장하지 않습니다.

## 기술 구성

- `web/`: 빌드 없이 실행되는 반응형 HTML/CSS/JS, `<video>` + Canvas, MediaRecorder.
- `backend/main.py`: FastAPI, 코드 인증, 경기 API, WebSocket, 영상 분석 작업, MP4 출력.
- `backend/engine.py`: MediaPipe 다인 포즈, 가까운 골반 위치 기반 임시 추적, OpenCV 흰 소형 이동물체 후보, 시계열 랠리 상태, 점수 이력 재계산.
- `scripts/download_model.py`: Google 공식 포즈 모델 다운로드.
- `data/`: 원본·출력 영상, 경기 점수/설정. 로컬 파일 시스템에 보관됩니다. 영상 작업 목록은 서버 메모리에 있어 재시작 후 다시 업로드해야 합니다.

CPU 추론으로 실행합니다. GPU 설치나 CUDA 설정을 요구하지 않습니다. 네 선수 포즈 검출은 가림과 원거리에서 누락·ID 교환이 생길 수 있습니다. 코트 평면 변환은 바닥상의 점에만 유효하며 공중 셔틀을 실제 착지 좌표로 확정하지 않습니다.

## 검증

```powershell
.venv/Scripts/python.exe -m unittest discover -s tests -p 'test_*.py' -v
node --check web/app.js
# 실행 중인 서버 + Playwright가 있을 때
node tests/browser.mjs
```

테스트는 점수 이전·취소·듀스·게임 종료 재계산, 충돌/비활성/상관 근거의 보류, 네 포즈 각각의 X, 제스처 중복·끊김·진행 중 차단, 코트 변환, 시계열 랠리→시험 자동 점수→X 수정, 실제 파일 업로드·모델 실행·MP4 길이, 브라우저 카메라 왕복과 모바일 넘침을 검사합니다.

합성 프레임 및 가상 카메라 통과는 실제 배드민턴 판정 정확도나 통신사망 성능 검증이 아닙니다. 현장 영상 검증 결과는 아직 없습니다.

## 다음 구현 순서

1. 외부 HTTPS 경로 연결 후 실제 휴대폰에서 10분 전송/발열/데이터 사용량 시험.
2. 본인 촬영 영상으로 랠리 경계·득점·X 동작 정답 데이터 작성. 경기/촬영일 단위로 학습/평가 분리.
3. WebRTC + TURN, 원본 녹화와 분석 경로 분리, 끊김 후 재업로드.
4. 셔틀·라켓 모델 연결, 타격/착지 증거와 영상+포즈 시계열 모델로 클리어 준비–스윙–복귀 확장.
5. 코치 검증 라벨로 자세 품질 모델 평가. 가림·낮은 화질에서는 평가를 보류.

웹앱은 지금의 프로토타입·파일 분석·PC 결과 조회에 적합합니다. 장시간 안정적 촬영, 백그라운드 녹화, 노출/셔터/프레임률의 세밀한 제어, 로컬 원본 보존이 핵심 요구가 되면 **네이티브 촬영 앱 + 동일한 PC 분석 서버 + 웹 대시보드**가 유리합니다. 네이티브로 바꿔도 통신사 업로드 속도와 영상 AI 정확도 문제는 남습니다.
